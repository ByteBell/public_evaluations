# OTel Metrics Extraction Prompt

Reusable prompt for extracting metrics from Claude Code OpenTelemetry `events.jsonl` and `metrics.jsonl` log files and appending them to a result `.json` file.

---

## Prompt

```
I have two OpenTelemetry log files generated by Claude Code for the run at:
  - events.jsonl: <PATH>
  - metrics.jsonl: <PATH>
  - result JSON to update: <PATH>

Parse both files and extract the following, then append the values to the result JSON file.

### From events.jsonl
OTel logs format — one JSON per line, nested under:
  data.resourceLogs[].scopeLogs[].logRecords[].attributes[]
Each attribute is a {key, value: {stringValue | intValue}} pair.

For api_request events (event.name = "claude_code.api_request"), SUM across all records:

| Field                        | Source attribute key   |
|------------------------------|------------------------|
| total_input_tokens           | input_tokens           |
| total_output_tokens          | output_tokens          |
| total_cache_read_tokens      | cache_read_tokens      |
| total_cache_creation_tokens  | cache_creation_tokens  |
| total_cost_usd               | cost_usd               |
| total_duration_ms            | duration_ms            |

For timing, use event.timestamp (ISO 8601) on the FIRST and LAST api_request events:

| Field               | How to compute                                                           |
|---------------------|--------------------------------------------------------------------------|
| time_taken_seconds  | (last api_request event.timestamp) - (first event.timestamp) in seconds  |
| start_time          | event.timestamp of the first api_request event (ISO 8601)                |
| end_time            | event.timestamp of the last api_request event (ISO 8601)                 |

Also extract:

| Field               | How to compute                                                           |
|---------------------|--------------------------------------------------------------------------|
| total_api_requests  | Count of records where event.name = "claude_code.api_request"            |
| total_tool_calls    | Count of records where event.name = "claude_code.tool_result"            |
| models_used         | Unique list of "model" attribute values from api_request events          |

### From metrics.jsonl
OTel metrics format. Look for metric name "claude_code.token.usage" with attribute "type":
  - "input"          → total_input_tokens  (cross-check with events sum)
  - "output"         → total_output_tokens
  - "cacheRead"      → total_cache_read_tokens
  - "cacheCreation"  → total_cache_creation_tokens

Look for metric name "claude_code.cost.usage":
  - total_cost_usd (cross-check with events sum)

NOTE: Claude Code OTel does NOT record a "thinking_tokens" attribute. The model's
visible reasoning in the UI is counted inside output_tokens. Always set
total_thinking_tokens = 0 unless a "thinking_tokens" key appears in the log records.

### Output — append these fields to the result JSON:

{
  "time_taken_seconds": <float>,
  "start_time": "<ISO8601>",
  "end_time": "<ISO8601>",
  "total_cost_usd": <float>,
  "total_input_tokens": <int>,
  "total_output_tokens": <int>,
  "total_cache_read_tokens": <int>,
  "total_cache_creation_tokens": <int>,
  "total_thinking_tokens": 0,
  "total_api_requests": <int>,
  "total_tool_calls": <int>,
  "models_used": ["<model_id>", ...]
}

Read the files strategically using offset/limit since they can be large.
For events.jsonl, iterate all lines. For metrics.jsonl, the last lines usually
contain final cumulative values. Report any fields that are missing or zero with a note.
```

---

## Schema Reference

| File | Protocol | Root path |
|------|----------|-----------|
| `events.jsonl` | OTel Logs | `data.resourceLogs[].scopeLogs[].logRecords[].attributes[]` |
| `metrics.jsonl` | OTel Metrics | `data.resourceMetrics[].scopeMetrics[].metrics[]` |

### api_request event attributes
`model`, `cost_usd`, `duration_ms`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `speed`, `event.timestamp`, `event.sequence`

### token.usage metric — type values
`"input"`, `"output"`, `"cacheRead"`, `"cacheCreation"` — no thinking type exists in Claude Code telemetry (as of 2026-03)

### Why thinking_tokens = 0
The Claude Code OTel harness does not emit a separate thinking token counter.
Extended thinking tokens visible in the UI are billed as output tokens and counted there.
